# 性能基线（P5）

本文件记录 1k / 10k / 100k 包下的解析、会话归表、模型插入、流视图渲染与内存占用，
用于回答两个问题：**界面会不会卡**、**20 万包上限下内存是否安全**。

## 1. 测试环境

| 项目 | 值 |
| --- | --- |
| 系统 | Windows 11 专业版 10.0.26200 |
| CPU | Intel Core i7-1165G7 @ 2.80 GHz（4 核 8 线程） |
| 内存 | 15.8 GB |
| Python | 3.12.9（64-bit） |
| Qt | PySide6 6.12.0 |
| 抓包驱动 | Npcap 1.90（libpcap 1.10.7，64-bit time_t） |
| 日期 | 2026-11-12 |

## 2. 方法

脚本：`python scripts/bench.py`（`--json` 输出机器可读结果，`--repeat` 控制重复次数取最小值）。

- 所有包使用**同一五元组**，流视图能拿到完整的 1k/10k/100k 个时序点；
- 「解析」是最坏情况：对全部包调用 `decode_packet` 构树。界面默认惰性解析，
  只解析可见行；但**启用显示过滤器后**代理模型要对每个新行求值，会退化为全量解析；
- 「会话归表」是 `SessionTable.add` 全量调用，含轻量 IP/L4 解析与 LRU 命中；
- 「模型插入」是 `PacketTableModel.append_batch` 一次批量插入，含会话归表与 Qt 行插入；
- 「流构建」是 `FlowView.set_flow`，含 `parse_flow` 全量解析与点排序；
- 「流渲染」是 1200×500 离屏 `QPixmap` 渲染一次，密集模式按像素列聚合；
- 「详情树」是 `DetailTree.show_layers` 清空并重建一棵字段树；
- 「内存」是 tracemalloc 峰值，**只覆盖包对象与原始字节**，不含 Qt 模型、索引与渲染缓冲。

## 3. 结果

| 包数 | 解析 (ms) | 解析 (包/秒) | 会话归表 (ms) | 模型插入 (ms) | 流构建 (ms) | 流渲染 (ms) | 详情树 (ms) | 峰值内存 (MB) |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 45.84 | 21,814 | 4.56 | 4.82 | 4.40 | 8.39 | 0.19 | 0.57 |
| 10,000 | 626.69 | 15,957 | 57.02 | 54.84 | 55.53 | 13.60 | 0.18 | 5.78 |
| 100,000 | 7,750.55 | 12,902 | 598.49 | 711.80 | 685.17 | 177.73 | 0.37 | 57.88 |

队列语义（容量 100,000，灌入 200,000）：丢弃 100,000，耗时 323.99 ms
（约 617,000 次 `put`/秒），丢包计数与容量严格一致。

帧预算换算：界面每 16 ms 取一批、上限 300 条。按 100k 包模型插入 711.8 ms 折算，
单批 300 条约 **2.1 ms**，占 16 ms 预算的 13%，60 fps 刷新仍有约 7 倍余量；
流视图单次**渲染** 13.6 ms（10k 点），不参与每帧刷新。

需要区分"构建"与"渲染"：`set_flow` 需要逐包 `parse_flow` + 排序，
10k 点约 **55.5 ms**、100k 点约 **685 ms**（见上表「流构建」列）。
选中流期间每秒会按新包重建，因此大流量流下不要长时间停留在流视图页签。

## 5. 已知性能边界

| 场景 | 影响 |
| --- | --- |
| 启用显示过滤器 | 每个新行都要 `decode_packet`，惰性解析失效；20 万包 + 过滤会明显卡顿 |
| 流视图大流 | 构建成本 10k≈55 ms、100k≈686 ms，每秒重建一次 |
| 进程归属快照 | 367 条约 4 ms；10k 连接线性外推约 110 ms，当前在 GUI 线程按 TTL/未命中刷新 |
| 会话面板刷新 | 抓包中每秒 `beginResetModel` 一次，2 万会话时会有一次可见重建 |

## 4. 与验收阈值对比

| 指标 | 阈值（NPS-Readme §5.2 / §5.6） | 实测 | 结论 |
| --- | --- | --- | --- |
| 10,000 包流时序图渲染 | ≤ 1,000 ms | **13.60 ms** | 通过，余量约 73 倍 |
| 详情树展开 | ≤ 100 ms | **0.18 ms** | 通过 |
| 20 万包内存 | < 800 MB | 10 万包 **57.9 MB**（Python 对象，线性外推约 116 MB） | 通过，余量充足 |
| 5,000 pps 持续抓包 | UI 无 > 500 ms 卡顿 | 全量解析 12,902–21,814 包/秒；界面惰性解析更快，5,000 pps 有 2.5 倍以上余量 | 通过 |
| 队列丢弃率 | < 1%（5,000 pps） | 100k 容量下正常速率不触发；超容量压测按预期丢弃并计数 | 通过 |

补充：P1 阶段实测进程内存为 5 万包时 59 → 120 MB（含 Qt），远低于 800 MB 上限。

## 5. 已落地的优化

| 优化 | 位置 | 效果 |
| --- | --- | --- |
| 惰性解析 + 按包序号缓存 | `PacketTableModel._decoded_for` | 只在 `data()` 被调用时解析，20 万包不会在插入时全量构树 |
| 批量插入 `beginInsertRows` 一次一批 | `PacketTableModel.append_batch` | 100k 包 711 ms（约 14 万包/秒），避免逐行信号风暴 |
| 流视图按像素列聚合 | `FlowView._draw_dense` | 10k 包只画 ≤ 1,050 列，13.6 ms 完成；文字仅在稀疏模式绘制 |
| `stream_id → 行号` 索引 | `PacketTableModel._stream_rows` | 按流取包从 O(N) 降为 O(k)；容量淘汰后索引失效并在下一次插入整体重建，避免半张索引少包 |
| 会话表 `version` + 快照缓存 | `SessionTable.version` / `SessionModel.refresh` | 空闲时每秒刷新从 O(n) 签名计算降为 O(1)；抓包时避免重复 `list()` 复制 |
| `memoryview` 零拷贝 | `Packet.raw` | 十六进制、导出、二次解析共用同一份字节，内存不随视图翻倍 |

## 6. 边界与未做

- **不做 TCP 重组**：流视图以包为粒度，重传与乱序按到达顺序展示；
- 密集模式下不标注单个包长，避免文字互相覆盖；放大到每包 ≥ 28 px 才逐包标注；
- 10 万包的 `FlowPoint` 列表常驻约 10 MB，随会话切换释放；不在后台为所有会话预构建；
- 解析仍在 GUI 主线程按需执行（未启用独立解析线程），惰性策略保证了可见行开销可控；
- 性能数据来自单机单次采样（每项取 3 次最小值），不同 CPU 与磁盘会有差异。

## 7. P6 进程归属开销（Windows）

`scripts/probe_process.py` 与集成测试实测：

| 项目 | 结果 |
| --- | --- |
| 本机连接快照 | 367 条精确连接 / 6 个本机地址，**4.1 ms** |
| 回环 TCP 首次归属（含快照） | 2.7 ms |
| 快照刷新间隔 | 2 s（TTL） |
| 归属调用时机 | 仅会话创建与首个载荷，不在每包路径 |

按 367 条 4.1 ms 线性外推，10,000 条约 110 ms，**高于需求文档 §7 的 30 ms 目标**。
当前缓解：TTL 2 s、只在会话边界触发、单次实测 < 5 ms；连接数达到数千时，
建议把快照构建移到后台线程（已保留 `refresh(force=True)` 接口）。
该偏差记录在 `docs/DEVLOG.md` 的 P6「问题与修正」，后续优化不阻塞本期验收。
