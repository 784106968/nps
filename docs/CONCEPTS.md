# 抓包层次与加密边界

理解"能抓到什么、抓不到什么"，比会调用 API 更重要。本文对应实验 1A 要求的
"抓包层次与分析层次"。

## 1. 抓包发生在哪一层

```text
应用层    HTTP / TLS / DNS          ← libpcap 只能看到明文，加密内容不可读
传输层    TCP / UDP / ICMP          ← 端口、标志位、seq/ack
网络层    IPv4 / IPv6               ← 源/目的地址、TTL、分片
链路层    Ethernet / 802.11 / PPP   ← MAC、EtherType；libpcap 从这里开始
物理层    电信号 / 光信号            ← 抓不到
```

libpcap 通过内核的 `AF_PACKET` 套接字取帧，**入口在链路层之上、协议栈处理之前**。
在 Linux 上它是 netfilter 的 `NF_IP_PRE_ROUTING` 之前的一站：数据帧先被 libpcap
（以及 tcpdump 的 BPF 程序）看到，然后才进入路由、NAT、iptables 规则。

由此得到两条推论：

1. 抓包能看到的**最多是链路上真实传输的字节**，凡是发送前就加密、接收后才解密的内容，抓包看不到明文；
2. 本机发出的包在 `NF_IP_LOCAL_OUT` 之后、`POST_ROUTING` 之前的路径上被抓到，
   因此"本机抓自己的包"看到的是**尚未被网卡驱动处理**的帧，与对端看到的存在时序与长度差异。

## 2. 抓包层次 vs 分析层次

| | 抓包层次 | 分析层次 |
| --- | --- | --- |
| 关注点 | 帧能不能取到、取全、取快 | 取到之后如何解释 |
| 关键手段 | 混杂模式、snaplen、内核缓冲、BPF 下推 | 分层解码、会话聚合、DPI、显示过滤 |
| 失败表现 | 丢包、截断、漏帧 | 标错协议、会话错乱、过滤不准 |

典型误区：把"抓不到"当成"分析不出来"。先确认 `ps_drop` 与 `ps_ifdrop`，
再谈解析。

## 3. 加密边界（Thor 思考题）

iOS 上的 Thor 能在安装描述文件后解析 HTTPS，原因是它让系统信任了一张根证书，
把自己变成中间人：**在端点完成解密，再转发**。它并不是"破解了 TLS"。

这说明：

- 加密是对抗**链路监听**的有效手段，抓包工具对 TLS 载荷无能为力；
- 能看到 HTTPS 内容的前提是**持有会话密钥或位于端点**，与抓包库的实现无关；
- 本项目明确**不实现** TLS 解密与中间人代理，只提取握手阶段的可见元数据（如 SNI）。

## 4. 两种过滤不是一个东西

| | 捕获过滤（BPF） | 显示过滤（P2） |
| --- | --- | --- |
| 位置 | 内核态，`pcap_compile` 后下推 | 用户态，作用于已抓到的包 |
| 作用 | 决定哪些包进入用户态 | 决定哪些包显示出来 |
| 代价 | 过滤越早，性能越好 | 不影响抓包，只影响视图 |
| 语法 | `tcp port 80`、`icmp` | `ip.src == 10.0.0.1 && protocol == http` |

显示过滤无法弥补捕获过滤失误：被 BPF 丢掉的包不会因为显示过滤而回来。

## 5. 混杂模式的边界

- 有线 + 集线器/镜像口：混杂模式能看到同网段其它主机的帧；
- 有线 + 交换机：只能看到广播、组播与发往本机的帧，**除非配置端口镜像**；
- 无线：混杂模式仅能收到本机相关帧，看到全部空口帧需要**监控模式**，两者机制不同；
- 回环适配器：不支持混杂模式，设置了也无效。
